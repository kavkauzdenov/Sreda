# Research Agent — автономное исследование бизнеса

## Зачем это

Модель Research Passport (миграция 074) описывала исследование как настройку:
пользователь выбирал цели, видел список провайдеров и их доступность, мог
отметить источники и фразы. Название раздела в интерфейсе — «Источники и
ограничения» — было третьим шагом из шести, и по сути являлось экраном
здоровья провайдеров.

Это неправильная модель продукта. Пользователю не должно быть важно, есть ли
у системы VK API или отдельный API отзывов: это внутренняя реализация. Его
вопрос — «что вы знаете о моём бизнесе и что вы сейчас делаете».

Research Agent перестраивает модель:

```
БИЗНЕС (уже создан пользователем: название + город)
   ↓
ИДЕНТИЧНОСТЬ        ← строится из карточки, без настройки
   ↓
ГИПОТЕЗЫ            ← проверяемые утверждения, не чек-лист
   ↓
ПОИСКОВЫЕ ЗАПРОСЫ    ← с назначением и обоснованием
   ↓
ДЕЙСТВИЯ            ← единица работы, аудируемый след
   ↓
ИСТОЧНИКИ / ФАКТЫ
   ↓
НОВЫЕ ГИПОТЕЗЫ      ← находка порождает следующий вопрос
   ↓
…пока есть смысл
```

## Минимальный вход

```json
POST /api/v1/businesses/{id}/intelligence/osint/research/start
{ "mode": "standard" }
```

Название и город уже есть — бизнес был создан раньше. Ничего настраивать не
нужно: ни API-ключей, ни провайдеров, ни списка источников, ни целей, ни
запросов. Режим `quick|standard|deep` влияет только на бюджет и глубину, а не
на «качество» — это один и тот же агент с разным объёмом.

Ответ: `{ runId, status, created, plan }`. Повторный вызов при активном
исследовании возвращает то же самое с `created: false` — второе исследование
не создаётся.

## Идентичность: не все поля равнозначны

`src/server/intelligence/osint/research/identity.ts`

| Тип | Вес | Почему |
|---|---|---|
| `phone`, `domain`, `address` | 1.0 | уникально опознают бизнес |
| `email`, `city`, `legal_name`, `social` | 0.6 | сужают круг |
| `name`, `region`, `country`, `category` | 0.25 | коллизионны по построению |

Название **всегда** слабое. «Ромашка» в Барнауле и «Ромашка» в Томске — разные
бизнесы, и объединение их по совпадению названия — главная ошибка OSINT.

`identityConfidence` нормирует сумму весов к `IDENTITY_TARGET_TOTAL = 2.2` и
насыщается по повторным значениям одного типа: третий телефон того же бизнеса
не добавляет уверенности. Калибровка: `name+city ≈ 0.39`, `+телефон ≈ 0.84`,
`+домен → 1.0`.

## Гипотеза

`src/server/intelligence/osint/research/hypothesis.ts`

```ts
{
  type: "website",
  statement: "У бизнеса есть собственный сайт",
  reason: "без сайта нельзя подтвердить ни контакты, ни услуги",
  purpose: "website",
  priority: 95,
  confidence: 0.39,
  subjectKey: "business",
  subjectValue: "кафе ромашка",
  dedupeKey: "website:business:кафе ромашка",
}
```

`reason` обязателен. Гипотеза без объяснения — чёрный ящик, а объяснимость
часть продукта: пользователь должен видеть, почему система ищет именно это.

Первый эшелон (сайт, упоминания, карты, соцсети, отзывы, юрлицо, публикации,
вакансии, филиалы) строится из идентичности. Второй порождается **находкой**:
обнаруженный домен даёт гипотезы «на сайте есть контакты», «перечислены услуги»,
«указан адрес», «есть вакансии».

Пустая попытка **снижает приоритет** (`decayPriority`), но не удаляет гипотезу.
Это торможение насыщения на уровне плана: ветка сворачивается вместо
бесконечного ползания по одному классу запросов.

## Запрос

`src/server/intelligence/osint/research/query-generator.ts`

Запрос — не строка, а обоснованное решение:

```ts
{
  query: "site:romashka-barnaul.ru контакты",
  purpose: "contact",
  priority: 70,
  derivedFrom: "На сайте romashka-barnaul.ru есть контакты",
  dedupeKey: "contact:domain:romashka-barnaul.ru:контакты",
  hypothesisKey: "contact:domain:romashka-barnaul.ru",
}
```

`dedupeKey` даёт идемпотентность, `derivedFrom` — объяснимость. Проверка домена
даёт `site:`-запросы, опознанный телефон — запрос по самому телефону: он
опознаёт бизнес точнее названия.

## Оценка следующего действия

`src/server/intelligence/osint/research/coverage.ts`

```
priority = (1.2·identityRelevance + 2·purposeGain·eig + 0.8·reliability
            + novelty + 0.6·eig) − (0.8·cost + 3·duplication)
```

Новизна и дублирование считаются по исходам **прошлых действий того же
направления**. Ветка без результата автоматически уступает fruitful, а не
продолжает занимать место в очереди.

Каждое действие получает человекочитаемое объяснение: «опирается на
подтверждённые данные», «похоже на уже изученное направление».

## Покрытие: не обещаем полноту

Покрытие считается по **подтверждённым направлениям**, а не по числу
скачанных страниц. Каждое измерение объясняет, что мешает его закрыть.
Полноту доказать нельзя, поэтому «100%» недостижимо, а пустое покрытие
низкое. Раздел «Пока неизвестно» обязателен: пустой список неизвестного
вводил бы в заблуждение сильнее, чем его отсутствие.

## Когда агент останавливается

| Причина | Что означает |
|---|---|
| `budget_exhausted` | исчерпан бюджет исследования |
| `no_useful_actions` | нет действий, способных дать новое знание |
| `information_gain_exhausted` | последние действия не дают новой информации |
| `coverage_sufficient` | основные источники найдены |

Агент обязан уметь остановиться **и сказать почему**. Иначе он либо крутится
вечно, либо врёт о завершённости.

## Источники: блокировка ≠ провал

`src/server/intelligence/osint/research/fallback.ts`

Раньше 403, 429, captcha, robots и timeout схлопывались в `http_error`, и агент
не мог отличить «смени маршрут» от «повтори позже». Теперь есть таксономия и
правило: **ни одна блокировка не останавливает исследование**.

| Причина | Повторять? | Действие |
|---|---|---|
| `robots_disallowed` | нет | искать тот же факт в другом месте |
| `captcha` | нет | искать через другой источник |
| `http_403` | нет | искать в другом месте |
| `requires_auth` | нет | опознать бизнес по другому идентификатору |
| `http_429`, `http_5xx`, `timeout` | да | пробовать другой, вернуться позже |
| `http_404` | нет | уточнить запрос |
| `private_address` | нет | искать другой источник |

Чего здесь нет и не будет: обхода CAPTCHA, подмены отпечатков, stealth-браузера,
прокси для обхода защиты, неуважения к `robots.txt` и обхода rate limits.
Приватный адрес — это отказ нашей SSRF-защиты, а не препятствие, которое
нужно обойти.

## Границы безопасности

**Детерминированным** остаётся всё, что связано с безопасностью и
идемпотентностью: нормализация URL, дедупликация, сопоставление сущностей,
хеширование, бюджеты, tenant isolation, права и переходы состояний.

Внешний контент — недоверенный ввод. Он используется как данные для извлечения
фактов и никогда как инструкция. Действующие инструкции по безопасности SSRF в
`safe-fetch.ts` не ослаблены: протоколы, приватные адреса, DNS-резолвинг,
редиректы, размер и тип содержимого — всё как было.

## Что считается чем

Термины различаются намеренно, и их нельзя смешивать:

| Термин | Что это | Пример |
|---|---|---|
| **Source** | источник, вещь в интернете | `https://romashka.ru/contacts` |
| **Observation** | что мы увидели у источника в конкретный момент | заголовок, текст, рейтинг, снимок |
| **Fact** | утверждение, извлечённое из observation | «телефон +7…» с `source_id` и `observation_id` |
| **Inference** | вывод из фактов | «вероятно, это филиал» |
| **Hypothesis** | проверяемое утверждение, ещё не доказанное | «у бизнеса есть сайт» |
| **Contradiction** | два разных значения одного поля из разных источников | телефон A и телефон B |

Факт не превращается в предположение: у него есть провенанс. Гипотеза не
превращается в факт, пока не подтверждена. Противоречие не разрешается молча —
`osint_intelligence_contradictions` хранит обе стороны и **не выбирает
победителя**.

## Слои данных

Глобальные и разделяемые: `osint_sources`, `osint_observations`,
`osint_entities`, `osint_source_access`, `osint_entity_*`. Один источник может
упоминать несколько бизнесов и не привязан ни к одному.

Tenant-scoped: `osint_discovery_runs`, `osint_research_actions`,
`osint_research_hypotheses`, `osint_source_candidates`, факты и находки.
Инвариант из миграции 070 сохранён: у глобальной таблицы нет `business_id` и
нет внешнего ключа на `business` или `user`.

## География данных

Российский VPS хранит всё: приложение, базу, бизнес-данные, находки OSINT.
NL-шлюз — только транспорт. Никакого нового хранилища на NL не появилось.

Технически схема соответствует принципу локализации. Это **не** означает
автоматического полного соответствия 152-ФЗ: трансграничная передача
персональных данных имеет самостоятельные юридические требования, которые
оцениваются отдельно.

## Ограничения

- Покрытие ограничено бюджетом и доступностью источников. Система ищет
  максимально широкий объём доступной публичной информации, но не обещает
  «всё вообще».
- Внешние поисковики без API-ключа ограничены тем, что доступно публично.
  Если конкретный провайдер недоступен, агент идёт другой веткой — но не может
  добыть то, чего публично нет.
- LLM в контуре извлечения отключён по умолчанию; инфраструктура работает без
  него. При включении внешний текст должен передаваться как недоверенные
  данные, а не как инструкция.

## Следующий логичный шаг

Сейчас планировщик выдаёт следующее действие, а исполняет его существующий
discovery-механизм со статическими шаблонами. Следующий шаг — замкнуть цикл:
факт, извлечённый enrichment'ом, должен порождать новую гипотезу
(«телефон найден → проверить его в независимых источниках»), а
противоречие — переоценку приоритетов («два разных адреса → искать историю
адреса»). Схема это уже позволяет: таблицы и dedupe-ключи на месте.
