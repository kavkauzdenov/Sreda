# Первое решение: приём заявок

## Этап 2: реализованный предпросмотр

Каталог `/solutions` сохраняет существующие 3D-assets и цветовую семантику решений. Доступен переход к `/solutions/leads/setup`. Остальные решения обозначены как будущие; ложного подключения нет.

Четыре шага: площадки → поля заявки → диалог глазами клиента → итог. Можно выбрать Telegram, VK или обе площадки. Имя обязательно, телефон/интерес/комментарий переключаются. Пример использует вымышленные ответы и не создаёт реальную заявку. Итог показывает состав настройки и цену из каталога, явно сообщает, что бот не подключён.

Настройка сохраняется в localStorage под версионированным ключом бизнеса. Сохраняются только типы площадок, идентификаторы полей и шаг. Смена бизнеса перемонтирует мастер и загружает соответствующий черновик. Повреждённое содержимое сбрасывается, неизвестные поля отбрасываются. Без площадки нельзя перейти дальше. Недоступность записи в браузере объясняется пользователю. Сброс доступен на desktop и mobile.

Это локальное удобство прототипа, а не авторизация или tenant isolation. На общем устройстве данные браузера доступны его пользователям. До настоящих аккаунтов переносим черновики на backend с проверкой BusinessMember и очисткой локальных данных при выходе. Секреты и реальные ответы клиентов в это хранилище не добавлять.

## Полный путь после подключения backend

| Шаг | Действие пользователя | Условие перехода / восстановление |
|---|---|---|
| Вход | Войти в аккаунт | Подтверждённая сессия; истечение возвращает к входу, не стирает серверный черновик |
| Бизнес | Назвать бизнес или выбрать существующий | Проверенное членство; сервер задаёт business_id, клиент не выбирает чужой tenant |
| Решение | Выбрать «Приём заявок» | Создаётся или возобновляется SolutionInstance в draft; повторный клик не создаёт дубль |
| Площадки | Подключить Telegram и/или VK | Каждое подключение подтверждает сервер. Неверный ключ объясняется, частичный успех сохраняется |
| Вопросы | Выбрать необходимые поля | Сервер валидирует конфигурацию и её версию; повторная попытка безопасна |
| Проверка | Отправить проверочную заявку через свой бот | Заявка помечена тестовой, показана в нужном бизнесе; таймаут предлагает повторить проверку |
| Подписка | Увидеть цену и подтвердить оплату | Только подтверждённое сервером событие платежа; возврат из оплаты сам по себе не активирует решение |
| Запуск | Нажать «Начать принимать заявки» | Каналы, конфигурация и entitlement готовы; Dashboard показывает реальное состояние |

Пользовательские тексты: «Подключите Telegram», «Создайте бота», «Скопируйте полученный ключ», «Бот подключён». В интерфейсе нет webhook, endpoint или transport adapter. Ключ передаётся только защищённому серверному действию и после сохранения не возвращается на клиент.

## Следующие этапы и критерии

3. **Ядро и контракты:** модульный backend, схема PostgreSQL, BusinessMember/роли, SolutionInstance, ChannelConnection, API-контракты и жизненный цикл. Одно бизнес-ядро для Web/TG/VK; никакого отдельного источника остатков или заявок в каналах. До runtime/deployment отдельно проверить локализацию данных и границы обработки персональных данных.
4. **Аккаунты и бизнесы:** вход, выбор/создание бизнеса, серверная авторизация каждого действия. Проверки запрещённого доступа между двумя бизнесами обязательны.
5. **Приём заявок:** серверные настройки, заявки, статусы и уведомления; идемпотентность входящих событий, аудит критических действий.
6. **Telegram:** безопасное подключение собственного бота, обработка входящих событий общим ядром, отзыв/ротация доступа, тестовая заявка.
7. **VK:** подключение сообщества через тот же контракт; проверка, что данные обеих площадок видны в одном бизнесе.
8. **Подписка и запуск:** подтверждённая модель платежей, ошибки/повторы, операционные проверки, затем ограниченный пилот.

Этапы не считаются завершёнными по наличию интерфейса или успешной сборке. Нужны проверки реального поведения, изоляции данных и адаптива. Продакшен, платежи и реальные секреты не включены в этап 2.

## Проверки этапа 2

Автотесты проверяют повреждённый JSON, несовместимую версию, неизвестные данные, обязательное имя, отсутствие площадок, некорректный шаг и отдельные ключи бизнесов. В браузере проверяются переход из каталога, валидация площадок, изменение полей, Telegram/VK-предпросмотр, итог, восстановление после перезагрузки, смена бизнеса и сброс. Контрольные ширины: 1440, 1280, 900, 390. Обязательные команды: npm test, npm run typecheck, npm run lint, npm run build.
