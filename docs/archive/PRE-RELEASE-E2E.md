# Подготовка к реальному E2E и выпуску

Дата проверки: 2026-09-16. Рабочая ветка: `codex/unified-business-foundation`, PR #19. Merge и production deploy не выполнялись. Staging подготовлен конфигурацией и диагностикой; реальные сервисы не подключались без credentials владельца.

## Дополнительные проверки и исправления

- Сквозные переходы Telegram/VK: незавершённая запись → администрация → заявка используют одного CRM-клиента и не поглощают команды меню старым сценарием.
- ID исходящих сообщений теперь включают платформу, подключение и чат: одинаковые Telegram message_id в разных чатах больше не конфликтуют после отправки.
- Отзыв сотрудника освобождает его активные заявки и диалоги только в нужном бизнесе, удаляет привязку уведомлений; история сохраняется.
- Длинные ответы и итог заявки разбиваются на сообщения до лимита платформы, без разрыва Unicode; кнопки находятся в последней части. Email заявки переносится в CRM.
- Создание заявки повторно проверяет membership после блокировки бизнеса.
- Проверены permission/scope, конкурентное бронирование и назначение диалога, повторные updates, доставка/retry, неопределённый результат отправки после сбоя, timezone/DST, recurring, вложения и AI-ошибки автоматическими тестами. Реальные API-провайдеры ими не заменяются.
- API принимает длинный Unicode-ответ в пределах лимита формы; неправильные UUID возвращают validation error вместо ошибки БД. Загрузка вложения повторно проверяет membership после S3 upload и удаляет объект при отзыве доступа.
- Автопостинг учитывает expires_at при выборе задачи и повторно проверяет активность под блокировкой бизнеса перед отправкой. При отмене доступа до сетевого вызова lease освобождается безопасно, без ложного неопределённого результата.
- Health web/БД отделён от общего health workers, чтобы остановленный worker не блокировал развёртывание web. Полный health сохраняет контроль требуемых активных решений.
- Формы и панели получили ограничения ширины, переносы текста и кнопок; CRM переходит в одну колонку на планшете. При изменении даты/специалиста очищаются старые слоты; переключение клиента/диалога во время сохранения/загрузки вложения ограничено.
- Каталог и главный экран показывают четыре реально работающих решения; удалена устаревшая production-карточка «Продажи», а переходы ведут в заявки, inbox, запись и публикации.
- Финальная локальная регрессия: 109 тестов, 100 успешно и 9 PostgreSQL-only пропусков, 0 ошибок; dependency audit — 0 уязвимостей. PostgreSQL race/HTTP/Docker остаются обязательной частью GitHub Verify.

## Миграции и сохранность данных

001–018 не изменены. Тест `tests/migration-upgrade.test.mjs` создаёт старую схему, наполняет все существовавшие таблицы данными (включая авторизацию, encrypted secrets, runtime, outbox, заявки и сообщения), сохраняет каждую старую колонку/строку, применяет 019–031 и сравнивает снимки. Повторный запуск не меняет ledger. В CI тест выполняется в изолированной схеме PostgreSQL 17; локально — PGlite. Новые связи/CRM-записи добавляются без перезаписи исходных данных. Миграция 031 добавляет составной FK и запрещает цели публикации через подключение другого бизнеса.

В ещё не выпущенной миграции 029 исправлена обработка старых пустых/длинных имён: нормализуется только копия имени нового клиента, исходные заявки/сообщения не меняются. **Если предыдущая версия 029 уже применялась к staging, checksum будет отличаться. Не менять ledger вручную и не отключать проверку. Использовать новый изолированный staging или восстановить его из снимка 001–018. Если такая миграция уже применена к production, остановить выпуск и подготовить отдельную совместимую корректирующую миграцию после изучения фактической истории.**

Тестовые данные не доказывают совместимость со всеми значениями реальной базы. Перед выпуском обязателен прогон на защищённой копии production с тем же расширением/версией PostgreSQL и проверка количества пользователей, бизнесов, подключений, заявок и сообщений. Сделать проверенный backup и восстановление. Не выполнять down-миграции поверх новых пользовательских данных; rollback согласовывать по снимку и журналу изменений.

## Staging: конфигурация

Использовать отдельные БД, private S3 bucket, тестового Telegram-бота, канал и VK-сообщество. Не подключать staging к production-боту: webhook у бота один.

| Переменные | Требование |
|---|---|
| `APP_URL` | Публичный HTTPS origin staging без пути и завершающего `/` |
| `DATABASE_URL` | Отдельный PostgreSQL, одинаковый у web/workers |
| `BETTER_AUTH_SECRET` | Стойкий секрет минимум 32 символа, одинаковый у web/workers; существующий секрет нельзя произвольно менять |
| `NEXT_PUBLIC_DATA_SOURCE` | `api` при сборке |
| `TELEGRAM_WEBHOOKS_ENABLED`, `VK_WEBHOOKS_ENABLED` | `true` после подготовки изолированных интеграций |
| `ATTACHMENT_STORAGE` | `s3` |
| `S3_ENDPOINT`, `S3_REGION`, `S3_BUCKET` | HTTPS endpoint, регион, private bucket с доступом web/workers |
| `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY` | Минимальные права чтения/записи/удаления объектов нужного bucket |
| `AI_API_TOKEN`, `AI_MODEL` | Серверный ключ и доступная модель Responses API |

Telegram/VK tokens вводятся в разделе «Подключения» и хранятся зашифрованно; они не являются NEXT_PUBLIC env. VK для публикации требует соответствующий publish token и права. Не присылать секреты в отчётах/скриншотах/логах.

1. Подготовить отдельное окружение с web и двумя worker processes (`npm run worker:telegram`, `npm run worker:vk`).
2. Выполнить `npm ci`, собрать в api mode. Миграции запускает штатный `npm run db:migrate`; pre-deploy использует этот же механизм и блокировку. Сначала проверить на копии БД.
3. Запустить web, `npm run worker:telegram` и `npm run worker:vk`. Общие задания autopost/booking reminders выполняются существующими worker loops, отдельные дубли worker не нужны.
4. `npm run staging:check` проверяет конфигурацию без вывода значений; `npm run staging:check -- --database` дополнительно **только читает** checksums миграций и heartbeat. Код 1 означает неготовность, не обходить её фиктивными credentials.
5. `/api/health/web` проверяет web/БД; `/api/health` — также требуемые workers. После активации решений остановка необходимого worker должна дать unhealthy, после рестарта — восстановление.
6. Подключить тестовые Telegram/VK через UI, завершить настройку и запуск. Endpoints: `/api/telegram/[id]`, `/api/vk/[id]`. Использовать выдаваемые приложением URL/секреты, не выдумывать id. Проверить Telegram secret header, VK confirmation/group/secret, неверные запросы не должны создавать записи.
7. Проверить загрузку, получение и отправку реального файла через S3; проверить права Telegram-бота в канале и VK publish token. AI должен создавать только редактируемый черновик.

## Телефон: пошаговый E2E

Подготовить два бизнеса A/B, owner, admin и двух operator, два клиентских аккаунта. Все действия выполнять с тестовыми контактами.

1. Войти/выйти, проверить регистрацию/PIN, восстановление доступа и переключение A/B. В A задать публичное название, контакты и timezone, отличающийся от timezone телефона.
2. Подключить Telegram и VK. Невалидный token даёт понятную ошибку; валидный действительно продолжает подключение. После настройки заявки запуск работает, бот приветствует названием A.
3. В боте оставить заявку: обязательные/необязательные поля, изменение итога, отмена, отправка. После ответа следующий вопрос, после отправки одно подтверждение. В CRM один клиент, все ответы, web/Telegram-уведомление сотруднику.
4. Два сотрудника открывают заявку; взять/завершить, проверить имя исполнителя и историю. Повторить клиента через сообщения/запись: карточка клиента общая. Одно имя у разных platform ID не должно автоматически объединять людей.
5. Написать администрации текст, фото, видео, документ и voice. Проверить inbox/unread отдельно у двух сотрудников. Одновременно взять диалог: только один получает назначение. Ответить текстом и вложением; клиент получает их в том же канале. Закрыть, написать снова, убедиться в сохранении истории.
6. В процессе незавершённой записи нажать администрацию, затем заявку. Проверить переходы без повторного приветствия старого сценария. Повторить в VK.
7. Создать услуги/специалистов, расписание с перерывом, выходной и индивидуальный день. Проверить свободные слоты, длительность и buffers, minimum notice/horizon. Два клиента одновременно подтверждают один слот: одна запись, второму понятная ошибка.
8. Создать ручную запись существующему/новому клиенту, открыть календарь день/неделя/список. Перенести, отменить с подтверждением, завершить/no_show. Проверить освобождение слота, CRM history и уведомления.
9. Создать тестовые записи для напоминаний 24h/2h (при необходимости подождать реальные границы на staging). Проверить кнопки переноса/отмены и отсутствие повторных напоминаний после рестарта worker.
10. Создать пост Telegram+VK с текстом, фото/альбомом/видео, ссылками/кнопками в поддерживаемом формате. Проверить сейчас, по расписанию business timezone, recurring, редактирование, отмену, дублирование. Отключить права одной тестовой площадки: виден partial/error, retry не повторяет успешную доставку.
11. AI: создать, сократить, переписать текст. Результат — draft; без нажатия публикации ничего не отправляется. Недоступный ключ/модель даёт понятную ошибку, обычное редактирование работает.
12. Переключиться в B: данные A не видны. Operator не меняет secrets/подключения/критические настройки. Отозвать operator A с активным диалогом/заявкой: работа доступна другому сотруднику, доступ отозванного закрыт, его членство в B не затронуто.

## Визуальная проверка

Браузер среды блокирует localhost (`ERR_BLOCKED_BY_CLIENT`); выполнен статический аудит, не заявляется пиксельная/визуальная приёмка.

После установки Chromium прогон запускается командой `AUDIT_BASE_URL=https://staging.example npm run audit:responsive`. Для закрытых страниц передать путь к локальному Playwright storage state через `AUDIT_STORAGE_STATE`; файл с сессией не коммитить и удалить после проверки. Скрипт проверяет 14 маршрутов на 390/768/1280/1440 px, HTTP/redirect, browser console и горизонтальное переполнение, а также сохраняет снимки четырёх основных рабочих разделов в `AUDIT_OUTPUT` (по умолчанию `/tmp/sreda-responsive-audit`).

| Ширина | Что проверить |
|---|---|
| 390 px, Safari/Chrome телефона | Нет горизонтального скролла; клавиатура не закрывает отправку; safe areas; нижняя навигация; диалоги подтверждения; длинные имена/username/ошибки; выбор даты, загрузка файлов и voice; кнопки доступны касанием |
| 768 px | CRM одна колонка; формы календаря/постов и inbox не зажаты; меню и фильтры переносятся |
| 1280 и 1440 px | CRM/inbox колонки, календарь и фильтры читаемы; модальные окна в viewport; нет чрезмерных фиксированных ширин |

На каждом размере проверить loading/empty/error/success, медленную сеть, повторное нажатие, обновление страницы, длинный список с «Загрузить ещё», большой текст и отсутствие утечки данных при переключении бизнеса.

- Выполнен реальный E2E выше, проверены actual permissions Telegram/VK, S3/AI и визуальная матрица; результаты привязаны к SHA.
- Прогон миграций на копии production, checksums, backup/restore, согласованный rollback, доступные ресурсы БД и storage.

- Получить отдельное разрешение владельца на merge и production deploy. После разрешённого выпуска — health, smoke login/бизнес/заявка/сообщение/запись/пост и контроль очередей.
